# Tools Reference

This file documents every tool that CrewAI agents can call during the EX04 pipeline.
All tools live in `src/hw4/crewai_tools/tools.py` and are registered with the `@tool` decorator.
Each tool is a stateless Python function — it does one job, takes explicit parameters, and
returns a JSON string that the calling agent can reason over.

## Quick Reference

| Tool | Registered name | Used by |
|------|-----------------|---------|
| [Load Graph Metrics](#tool-1-load-graph-metrics) | `Load Graph Metrics` | Graph Navigator, Architect Detective, Quality Gate |
| [Read Obsidian Navigation Files](#tool-2-read-obsidian-navigation-files) | `Read Obsidian Navigation Files` | Graph Navigator |
| [Read Source File Snippet](#tool-3-read-source-file-snippet) | `Read Source File Snippet` | Fix Strategist |
| [Run Unit Tests](#tool-4-run-unit-tests) | `Run Unit Tests` | Quality Gate |

## Tool 1: Load Graph Metrics

**Registered name:** `Load Graph Metrics`  
**Source:** `src/hw4/crewai_tools/tools.py` — `load_graph_metrics()`

### What it does

Reads a `graph.json` file produced by Grphify and computes structural metrics of the
code dependency graph. It counts every node and edge, detects communities, finds bridge
edges (connections whose removal would disconnect parts of the graph), and ranks the
top 20 most-connected nodes (hubs) by degree.

This is the **entry point** of the agent reasoning phase. An agent calls this tool first
to understand the shape of the codebase before looking at any source code.

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `graph_json_path` | `str` | required | Absolute or relative path to `graph.json` |

### Returns

A JSON string with the following fields:

```json
{
  "node_count": 278,
  "edge_count": 517,
  "community_count": 15,
  "bridge_count": 127,
  "top_20_hubs": [
    ["exceptions_undefinedvariableintemplate", 21],
    ["exceptions_cookiecutterexception", 20],
    ...
  ],
  "edge_type_counts": {
    "Extracted": 380,
    "Inferred": 97,
    "Ambiguous": 40
  }
}
```

| Field | Meaning |
|-------|---------|
| `node_count` | Total Python symbols (classes, functions, modules) in the graph |
| `edge_count` | Total dependency edges (calls, imports, inheritance) |
| `community_count` | Number of distinct subsystems detected by NetworkX community detection |
| `bridge_count` | Edges whose removal would split the graph — potential SPOFs |
| `top_20_hubs` | List of `[node_id, degree]` sorted highest-first; hubs are bug candidates |
| `edge_type_counts` | How many edges are Extracted (certain), Inferred (probable), or Ambiguous |

**Why degree matters:** A node with degree > 10 is a HUB — it has too many dependencies
flowing through it, making it a bottleneck and coupling risk.

### Used by

- **Graph Navigator** (Stage 2, Task 1) — calls this as its very first action to produce the graph summary
- **Architect Detective** (Stage 2, Task 2) — may re-query if it needs to verify specific degrees
- **Quality Gate** (Stage 2, Task 4) — may call to check `hub_count` after the fix is proposed

### When it is called

At the start of Stage 2. The Graph Navigator calls it on `artifacts/graph.json` (the
before-fix graph). The Quality Gate may call it on `artifacts/graph_after.json`
(the after-fix graph) to compare hub counts.

## Tool 2: Read Obsidian Navigation Files

**Registered name:** `Read Obsidian Navigation Files`  
**Source:** `src/hw4/crewai_tools/tools.py` — `read_obsidian_files()`

### What it does

Reads two navigation files from the Obsidian vault — `hot.md` and `index.md` —
and returns their contents (truncated to a configurable character limit).

- **`hot.md`** lists the architecturally "hot" files: the nodes with the most connections,
  sorted by degree. It is generated by Grphify's Obsidian sync step.
- **`index.md`** is the vault's table of contents: one entry per detected community/module,
  linking to individual node pages.

Together these two files give the Graph Navigator a human-readable map of the codebase
without requiring it to read any actual Python source code.

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `obsidian_dir` | `str` | required | Path to the Obsidian vault directory (e.g., `obsidian/`) |
| `max_chars` | `int` | `2000` | Maximum characters to return per file (token budget control) |

### Returns

A JSON string mapping filename to truncated content:

```json
{
  "hot.md": "# Hot Files\n\n1. exceptions.py — degree 21\n2. main.py — degree 16\n...",
  "index.md": "# Vault Index\n\n## Community 0\n- [[exceptions]]\n..."
}
```

If a file does not exist in the vault, it is silently omitted from the result.

### Used by

- **Graph Navigator** only — uses it to get a plain-English summary of which files
  are architecturally important before reporting to the Architect Detective.

### When it is called

Immediately after `Load Graph Metrics` in the graph_summary_task (Stage 2, Task 1).
The Graph Navigator combines the structural metrics from the graph with the narrative
context from the Obsidian files to produce a richer summary.

**Token efficiency note:** By limiting to `max_chars=2000` per file, the tool returns
at most ~4000 characters total — roughly 1000 tokens — instead of sending all 18
source files (~23,000 tokens) to the agent.

## Tool 3: Read Source File Snippet

**Registered name:** `Read Source File Snippet`  
**Source:** `src/hw4/crewai_tools/tools.py` — `read_source_snippet()`

### What it does

Reads the first `max_chars` characters of any Python source file by path and returns
the raw content as a string. This lets the Fix Strategist inspect the actual code of
a hot file before writing a refactor proposal — without reading the entire file.

If the file does not exist at the given path, the tool returns a `"File not found: ..."` 
error string instead of raising an exception, so the agent can gracefully handle bad paths.

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `file_path` | `str` | required | Full or relative path to the Python source file |
| `max_chars` | `int` | `1500` | Maximum characters to read (keeps token cost low) |

### Returns

The raw file content as a plain string (not JSON), truncated at `max_chars`:

```
"""Exceptions for Cookiecutter."""

from __future__ import annotations
from typing import TYPE_CHECKING, Any
...
```

Or, if the file is not found:

```
File not found: data/cookiecutter/cookiecutter/exceptions.py
```

### Used by

- **Fix Strategist** only — called in fix_proposal_task (Stage 2, Task 3) to read the
  source file of the top-severity bug before writing the refactor proposal.

### When it is called

After the Architect Detective has identified the top bug and its source file. The Fix
Strategist receives the bug list in its context, extracts the `source_file` field from
the highest-severity bug, and calls this tool to read its content before deciding
what to extract.

**Design rationale:** The 1500-character limit means the agent reads just enough to
understand the class/function structure and propose a split — not the entire file.
For a 150-line file this covers about 70% of the content, which is sufficient for
proposing a structural refactor.

## Tool 4: Run Unit Tests

**Registered name:** `Run Unit Tests`  
**Source:** `src/hw4/crewai_tools/tools.py` — `run_unit_tests()`

### What it does

Runs the project's unit test suite with coverage measurement and returns a structured
verdict. It executes:

```bash
uv run pytest tests/unit -q --cov=src --cov-report=term-missing
```

Then it parses the pytest output to extract the total coverage percentage from the
`TOTAL` line and packages the result as JSON.

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `project_root` | `str` | `"."` | Working directory to run pytest from |

### Returns

```json
{
  "passed": true,
  "coverage_percent": 93.85,
  "output_tail": "114 passed in 15.96s\n..."
}
```

| Field | Meaning |
|-------|---------|
| `passed` | `true` if pytest exit code was 0 (all tests green) |
| `coverage_percent` | Parsed from the `TOTAL` line of pytest-cov output |
| `output_tail` | Last 800 characters of stdout — useful for diagnosing failures |

**Coverage threshold:** The Quality Gate agent uses `coverage_percent >= 85` as one
of its three PASS conditions. The `pyproject.toml` also enforces this via `fail_under = 85`.

### Used by

- **Quality Gate** only — called in verification_task (Stage 2, Task 4) to verify
  that the fix did not break any tests and that coverage remains above 85%.

### When it is called

At the end of the agent pipeline, in the Quality Gate's verification_task. By the time
this tool runs, the fix has already been applied to the source file (Stage 3 commits
the change). The tool verifies that the modified codebase still passes all tests.

**Note:** This tool does NOT apply any fix itself — it only measures the current state
of the codebase. The actual fix is applied by `GenericFixApplier` in Stage 3, which
runs outside the CrewAI agent loop (before the Quality Gate evaluates the result).
